# 用語集（勉強用）

Flutter 版のコードに出てくる用語の一覧。README には載せず、ここにまとめる。
「授業」の列は、アプリケーション開発演習でいつ扱う（扱った）かの目安。

## Dart

| 用語 | 意味 | このアプリのどこで使っているか | 授業 |
|---|---|---|---|
| Null Safety | 「null が入るかもしれない値」を型で区別する仕組み。`String?` は null かもしれない、`String` は必ず文字がある | `Live.venue`（会場は任意なので `String?`） | #2 |
| `final` / `const` | `final` は一度入れたら変えない値。`const` はアプリを作る（コンパイルする）時点で決まっている値 | 各クラスのフィールド、色の定義 | #2 |
| `required` | 名前付き引数を「必ず渡す」と決める | `Live({required this.id, ...})` | #2 |
| クラス・コンストラクタ | データと処理をまとめた型。コンストラクタはそれを作るときの入口 | `models/live.dart` | #2 |
| getter | 値を計算して返すプロパティ。`()` を付けずに呼べる | `_currentSongs`（今のモードの曲名） | #2 |
| `enum` | 決まった選択肢だけを持つ型 | `SongSort`（演奏回数順・最近やった順・曲名順） | #2 |
| `abstract interface class` | 「こういうメソッドを持つ」という約束だけを決めたクラス。中身は別のクラスが `implements` で書く | `ArchiveRepository` | #2（演習 2-F） |
| `Future` / `async` / `await` | `Future` は「あとで結果が届く」値。`await` で届くまで待つ。待つ処理を書く関数には `async` を付ける | 通信する関数すべて | #2 |
| `Future.wait` | 複数の `Future` を同時に始め、全部終わるのを待つ | `home_screen.dart` の `_reload` | #2 の発展 |
| `Stream` | 値が次々に届く流れ | ログイン状態の変化（`onAuthStateChange`） | #2（問題 2-E） |
| `try` / `catch` / `on` | 失敗（例外）を受け止める。`on AuthException` は特定の種類の失敗だけを受け止める | ログイン・保存・削除 | #2 |
| 純粋関数 | 同じ入力なら必ず同じ結果を返し、外の状態を書き換えない関数。テストしやすい | `logic/setlist.dart` | ― |
| `String.fromEnvironment` | アプリを起動するときに外から渡した値を読む | `main.dart` の Supabase の URL と鍵 | ― |

## Flutter

| 用語 | 意味 | このアプリのどこで使っているか | 授業 |
|---|---|---|---|
| Widget | 画面の部品。Flutter の画面はすべて Widget の組み合わせ（Widget ツリー） | すべての画面 | #4 |
| StatelessWidget | 自分では状態を持たない部品。渡された値をそのまま表示する | `MessageView`、`_SetlistCard` | #4 |
| StatefulWidget / `setState` | 状態を持つ部品。`setState` で状態を変えると、その部品が描き直される | 曲一覧の検索語、編集画面の入力 | #4 |
| `initState` / `dispose` | 部品が作られたとき・捨てられるときに 1 回だけ呼ばれる。準備と片付けに使う | 通信の開始、入力欄の片付け | #4〜 |
| `mounted` | その部品がまだ画面にあるか。`await` のあいだに画面が閉じられていたら `setState` してはいけない | 通信のあとの `if (!mounted) return;` | ― |
| `key` | Flutter が「どの部品がどれか」を見分ける目印 | 曲の並べ替え（`ObjectKey`）、ログインし直し（`ValueKey`） | ― |
| `TextEditingController` | 入力欄の中身を読み書きするための道具。使い終わったら `dispose` する | ログイン画面・編集画面 | #5 |
| Material Components | Google のデザインの決まり（Material Design）に沿った部品。`Scaffold`、`AppBar`、`TabBar`、`FilledButton`、`TextField` など | すべての画面 | #5 |
| `Theme` / `ThemeData` | アプリ全体の色・フォントを 1 か所で決める仕組み | `theme.dart` | #5 |
| `Navigator` | 画面を重ねたり（push）閉じたり（pop）する仕組み。`pop` で値を返せる | 編集画面を閉じて「保存した」を返す | #6 |
| `showModalBottomSheet` / `showDialog` | 下から出る画面、確認のダイアログを出す | 編集画面、削除の確認 | #6 |
| `StreamBuilder` | `Stream` に値が届くたびに描き直す部品 | `AuthGate`（ログイン状態で画面を出し分け） | #6〜#7 |
| `ListView.builder` | 画面に見えている行だけを作るリスト。件数が多くても重くならない | 曲一覧 | #5 |
| `RefreshIndicator` | 下に引っ張ると再読み込みする部品 | 曲一覧・ライブ | #5 |
| `pubspec.yaml` | 使うパッケージやフォントを書く設定ファイル | フォントの同梱 | #4 |
| `flutter test` | テストを実行するコマンド | `test/setlist_test.dart` | #9 |

## Supabase・設計

| 用語 | 意味 | このアプリのどこで使っているか | 授業 |
|---|---|---|---|
| API 通信 | アプリからサーバーにデータを頼み、結果を受け取ること | `api/` フォルダ | #7 |
| 外部ライブラリ（パッケージ） | 他の人が作って公開している部品。`pubspec.yaml` に書いて使う | `supabase_flutter` | #7 |
| Supabase | 認証（ログイン）とデータベースをまとめて提供するサービス | ログイン・データの保存 | ― |
| RLS（Row Level Security） | DB の「行」ごとに、誰が読み書きできるかを決める仕組み。他人のデータが見えないのはこれのおかげ | `../supabase/schema.sql` | ― |
| anon key | アプリに入れてよい公開用の鍵。これだけでは RLS を越えられない | `env.json` | ― |
| RPC | DB に用意した関数を呼ぶこと | `save_live` | ― |
| トランザクション | 複数の書き込みを「全部成功」か「全部なかったことに」のどちらかにする仕組み | `save_live` の中 | ― |
| ビュー | SQL の結果を表のように扱えるようにしたもの | 集計の `song_stats` | ― |
| Repository（リポジトリ）パターン | データの取得・保存をまとめた窓口を作り、画面からは窓口だけを使う設計 | `ArchiveRepository` | #8 |
| DI（依存性の注入） | 部品が使うもの（ここでは Repository）を、部品の中で作らず外から渡すこと。差し替えやテストがしやすくなる | `HomeScreen(repository: ...)` | #8 |
| ユニットテスト | 関数 1 つ 1 つが正しく動くかを確かめるテスト | `test/setlist_test.dart` | #9 |
| Widget テスト | 画面を仮に組み立て、タップや入力をして表示を確かめるテスト。`testWidgets` で書く | `test/home_screen_test.dart` | #9 |
| `pumpWidget` / `pumpAndSettle` | テストで画面を組み立てる／アニメーションや待ちが落ち着くまで画面を進める | `test/home_screen_test.dart` | #9 |
| `find` / `expect` | `find` で画面の中の部品を探し、`expect` で「こうなっているはず」を確かめる | `test/home_screen_test.dart` | #9 |
| フェイク（偽物） | テストのために本物の代わりに渡す、決まった値を返すだけの部品。呼ばれた内容を記録しておける | `test/fake_archive_repository.dart` | #8〜#9 |
| CI（継続的インテグレーション） | push のたびにテストなどを自動で実行し、壊れていないかを確かめ続けること | `.github/workflows/ci.yml` | #9 |
| GitHub Actions | GitHub に用意されている CI の仕組み。設定は `.github/workflows/` の YAML ファイルに書く | `.github/workflows/ci.yml` | #9 |
| 静的解析 | プログラムを動かさずに、書き方のミスや危ない書き方を探すこと。`flutter analyze` | CI | ― |
